# PF3 怎样组织项目续接

[English](design.md) · [展示入口](../README.zh-CN.md)

新 AI 窗口需要知道当前在做什么、哪些结论仍然有效，以及它可以改动什么。PF3 的项目模型为这些问题安排了明确的位置。本文是作者对当前设计的说明；可运行的证据见[实测记录](evidence.md)与[仓库范围](../README.zh-CN.md#范围与证据)。

## 五状态区分准备、执行和结论

| 状态 | 下一位接手者应该理解什么 |
|---|---|
| `planned` | 提出了这项工作，还没有开始。 |
| `active` | 这是该路线当前正在推进的工作。 |
| `paused` | 工作已经开始，暂时停下，结果仍未定。 |
| `done` | 这次尝试已经形成完成结论。 |
| `failed` | 这次尝试已经形成失败结论，并留下原因。 |

关键区别是“暂停”与“形成结论”。缺少输入可以导致暂停，而原来的做法仍可能成立。失败则留下下一位接手者再次尝试前需要考虑的结论。原因、证据和决定补充在状态旁边。

每条路线同时最多有一个 active 节点。节点顺序展示此前的尝试、当前落点和后续计划。五状态是为这套工作流选定的词汇，属于设计取舍；它没有证明所有项目系统都必须恰好使用五种状态。

## 路线版本覆盖涉及多个节点的判断

“一条路线最多有一个 active”涉及整条路线。激活一个节点时，需要知道同一路线是否已有其他 active 节点，因此节点流转与路线编辑以路线版本作为校验依据。

若只给每个节点独立版本，仍需要跨节点协调才能维持这项约定。统一的路线版本让调用者知道这一致性边界在哪里。代价是冲突范围更大：同一路线上本来互不相关的工作，也可能互相触发版本冲突而需要重读。这是作者少量 AI 客户端工作流下的选择，繁忙团队是否适用，需要另行评估。

公开示例用 `revision`、`summary` 和 `nextStep` 单独展示旧版本写回的检查。读者可以亲自运行这项性质，查看调用者如何恢复；这里的路线设计说明它在更大工作流中的用途。

## 继续工作时，保留已执行尝试的结论

正常路线编辑会保留已有执行记录的节点。失败尝试需要写明原因。再次尝试时，新建一轮并关联旧节点，让接手者能够区分“这个做法在当时条件下失败了”和“现在依据变化后的前提再试一次”。已完成工作重开时也沿用这一原则。

尚未开始的计划仍然容易修改或删除。这样既让规划保持轻量，也保留已做工作原本的含义，代价是需要展示更长的历史。回执用于查看变更；支持撤销的操作可通过明确的更正或撤销处理。保留一次尝试的结论，并不意味着每次写入都不可逆。

## 规则跟着它影响的工作走

| 范围 | 用途 |
|---|---|
| 跨项目规则 | 影响多次后续交接的长期规则，由所有者审阅 |
| 项目规则 | 在一个项目内持续适用的决定 |
| 节点约束 | 指向一个明确后续节点的具体条件 |

节点约束随需要它的节点出现。节点关闭时，明确它已经被吸收，或在适用范围更广时升级为项目规则。准备跨项目适用的规则，再经过相应的审阅路径。

这为每条指令限定了存续时间和阅读对象，也增加了一项关闭工作：调用者需要判断哪些已被使用、哪些仍然适用。跨项目规则之间出现冲突时，交由明确决策处理，不让系统仅凭优先级数字自动选边。

## 续接包把当前工作摆在面前

PF3 汇集适用规则、必要项目背景、当前节点、写回信息和相关资产引用；尚未定义的内容会明确标出。代码、报告等资产仍可在它们原本的位置按需打开。

接手者应该能够回答：接着做什么，什么结论把工作带到这里，哪些约束适用，读取的是哪个版本，要留下什么结果。组织这些答案，是 PF3 处理的续接问题；版本检查让一次写回与它依据的状态相联系。

## 在一次试点里验证什么

选一个真实流程，观察一次交接：新客户端能否找到当前任务及相关的旧决定或失败，定位必要输入，完成约定动作，并留下下一个客户端可以核验的结果？实施前先为这个流程约定验收标准。

公开契约测试提供一个小型、可执行的基线。上面的设计取舍，则为合作方提供围绕真实工作流可以进一步验证的问题。
