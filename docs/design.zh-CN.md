# PF3 怎样组织项目续接

[English](design.md) · [展示入口](../README.zh-CN.md)

新 AI 窗口需要知道当前在做什么、哪些结论仍然有效，以及它可以改动什么。PF3 的项目模型为这些问题安排了明确的位置。本文是作者对当前设计的说明；可运行的证据见[实测记录](evidence.md)与[仓库范围](../README.zh-CN.md#范围与证据)。

## 先看一棵合成项目树

下面沿用截图中的「Demo · 缓存到底有没有用」，续写一次合成交接。②「试内存缓存」已是 failed：key 含请求时间戳，命中率只有 11%，失败原因保留在旧节点上。在这段续写里，④「按 key 的形状重切缓存」以去掉时间戳作为新前提，重开（reopens）②，并附上一条约束：“先检查 key 的形状与复用情况，再按原判据验证”。④完成验证并关闭时，若这条约束仍适用于本项目后续的缓存实验，就将它升级（promote）为项目规则，供⑤「写成一条规则」和后续相关节点使用。

## 五状态区分准备、执行和结论

| 状态 | 下一位接手者应该理解什么 |
|---|---|
| `planned` | 提出了这项工作，还没有开始。 |
| `active` | 这是该路线当前正在推进的工作。 |
| `paused` | 工作已经开始，暂时停下，结果仍未定。 |
| `done` | 这次尝试已经形成完成结论。 |
| `failed` | 这次尝试已经形成失败结论，并留下原因。 |

关键区别是“暂停”与“形成结论”。缺少输入可以导致暂停，而原来的做法仍可能成立。失败则留下下一位接手者再次尝试前需要考虑的结论。原因、证据和决定补充在状态旁边。

每条路线同时最多有一个 active 节点。节点顺序展示此前的尝试、当前落点和后续计划。

## 路线版本覆盖涉及多个节点的判断

“一条路线最多有一个 active”涉及整条路线。激活一个节点时，需要知道同一路线是否已有其他 active 节点，因此节点流转与路线编辑以路线版本作为校验依据。

若只给每个节点独立版本，仍需要跨节点协调才能维持这项约定。统一的路线版本让调用者知道这一致性边界在哪里。代价是冲突范围更大：同一路线上本来互不相关的工作，也可能互相触发版本冲突而需要重读。这是作者少量 AI 客户端工作流下的选择，繁忙团队是否适用，需要另行评估。

公开示例用 `revision`、`summary` 和 `nextStep` 单独展示旧版本写回的检查。读者可以亲自运行这项性质，查看调用者如何恢复；这里的路线设计说明它在更大工作流中的用途。

## 继续工作时，保留已执行尝试的结论

正常路线编辑会保留已有执行记录的节点。失败尝试需要写明原因。再次尝试时，新建一轮并关联旧节点，让接手者能够区分“这个做法在当时条件下失败了”和“现在依据变化后的前提再试一次”。已完成工作重开时也沿用这一原则。

尚未开始的计划仍然容易修改或删除。这样既让规划保持轻量，也保留已做工作原本的含义，代价是需要展示更长的历史。回执用于查看变更；支持撤销的操作可通过明确的更正或撤销处理。保留一次尝试的结论，并不意味着每次写入都不可逆。

## 规则跟着它影响的工作走

| 范围 | 用途 |
|---|---|
| 跨项目规则 | 影响多次后续交接的长期规则，由所有者审阅 |
| 项目规则 | 在一个项目内持续适用的决定 |
| 节点约束 | 指向一个明确后续节点的具体条件 |

节点约束随需要它的节点出现。节点关闭时，明确它已经被吸收，或在适用范围更广时升级为项目规则。准备跨项目适用的规则，再经过相应的审阅路径。

这为每条指令限定了存续时间和阅读对象，也增加了一项关闭工作：调用者需要判断哪些已被使用、哪些仍然适用。跨项目规则之间出现冲突时，交由明确决策处理，不让系统仅凭优先级数字自动选边。

## 续接包把当前工作摆在面前

### 接着做什么？

PF3 把当前节点的目标、通过条件和边界摆在面前，让新窗口从当前落点继续，例如合成树中的④「按 key 的形状重切缓存」。

### 什么结论把工作带到这里？

PF3 把当前节点引用的已有结论和依据入口放在一起，供接手者查看相关结果，例如②记录的低命中率及失败原因。

### 哪些约束适用？

PF3 提供当前适用的跨项目规则、项目规则与指向当前节点的约束；在这段续写里，④接到的是“先检查 key 的形状与复用情况，再按原判据验证”。

### 读的是哪个版本？

PF3 把读取时的路线版本与相应写回要求放在一起，供需要版本校验的写入使用，让写回对应到本轮读取的状态。

### 要留下什么结果？

PF3 把通过条件和交接要求摆在面前，让本轮交代做了什么、凭什么判断、下一步做什么；④关闭时还需要处置指向它的约束。

代码、报告等资产仍在各自的位置，接手者通过引用按需打开。

## 哪些由系统组装，哪些仍需执行者判断

人和 Agent 在工作中填写进展、决定、证据与引用。续接编译器在读取时从这些已保存的状态中组装视图，不会从聊天中自动补出尚未记录的决定，也不证明写入的结论为真。

视图包含生效的全局规则、项目规则与指向当前节点的待处置约束。当前节点的进展按三类保留最新记录：接力进展（progress 或 problem）、decision、evidence；其他历史仍可通过节点读取获得。项目资产位置作为待核验的声明提供给接手者。

界面中的 token 数是包体量的估算，不是预算分配或自动上限。明确范围、选择进展有助于组织上下文，但不保证所有项目的续接包都很小。

一份交接文档也能保存原因、规则和历史。PF3 把它们的组织与带版本的写回接成共享流程，让新窗口从已记录的项目状态开始。[MountainRS 的例子](mountainrs.zh-CN.md#从续接包读到原始记录)是先读续接包，再打开相关失败和暂停节点，无需从前一段聊天重建这些结论。

## 在一次试点里验证什么

选一个真实流程，观察一次交接：新客户端能否找到当前任务及相关的旧决定或失败，定位必要输入，完成约定动作，并留下下一个客户端可以核验的结果？实施前先为这个流程约定验收标准。

公开契约测试提供一个小型、可执行的基线。上面的设计取舍，则为合作方提供围绕真实工作流可以进一步验证的问题。
